Nastya and Katya created an initial draft of the interview answers for the official FI instagram post about RateUKMA.

_1. Як виникла ідея створити RateUKMA?_
Під час сезону запису ми питають у всіх "а як вам курс?" - у бадді, в чатах і тд і тп. Бадді скидали графіки, скатерплоти, відгуки і ми подумали - а як загорнути це в одну зручну платформу? Аналогічно, коли ми залишали відгуки на курси в офіційному опитуванні, було питання - а як потім почитати їх, щоб бути готовими до того, що буде на курсі?

Восени 2025 почався курс МРПС (Методи розробки програмних систем), ми зібрались в команду, Андрій з Міланою нагадали за ідею вище і так народився RateUKMA!

_2. Що мотивувало вас працювати над цим проєктом?_
Ми починали з того, що хотіли обрати для курсу МРПС реальний продукт — не черговий to-do list, а щось, чим справді будуть користуватись студенти
Тому благородна мета - робити Могилянку кращою для самих могилянців. Бо нам не все одно!
Колективно-егоїстична - дійсно мати ресурс, де можна почитати відгуки на курси. 
І приємний бонус - пет проджект в сіві, практика, хороша оцінка)))

_3. Що було найскладнішим у вашій частині роботи?_
Вписуватись у графіки курса)) Бо ми робили багато чого kinda production-ready, щоб це потім реально використовувалось, і тому витрачали достатньо багато часу на екстра речі поза домашками курсу. Після закінчення курсу - поєднувати роботу з пет-проектом з нашими роботами за гроші, навчанням та курсовою.

_По технічній складовій було б класно, якщо розкажете якісь цікаві речі:_
_1. Які технології чи інструменти ви використали?_
Фронтенд - 
React 19 with TypeScript,
TanStack Router for file-based routing,
Tailwind CSS for styling,
shadcn/ui for component library,
Biome for linting and formatting,
Vitest for testing
Orval для автогенерації типізованого API-клієнта з OpenAPI-специфікації

Бекенд - 
Django with Django REST Framework,
PostgreSQL database,
Redis for caching,
Python 3.11+,
OpenAPI documentation,
pytest for testing,
ruff for linting

Infra - 
AWS EC2,
GitHub as VCS,
GitHub Actions for CI/CD pipelines, 
GitHub Container Registry for images storage,
Docker + docker compose for containerization,
pre-commit hooks for local code and commits quality



Архітектура:
  - Фронтенд і бекенд знаходились в одному монорепо. OpenAPI-контракти зберігались спільно + Orval автоматично генерував типізований клієнт - завдяки цьому фронт і бек завжди були синхронізовані і було неможливо залити застарілий фронтенд.
  - Бекенд побудований на Domain-Driven Design (DDD) патернах: Repository Protocol → Frozen Dataclass DTOs → IoC
  Container з dependency injection. Репозиторії повертають не ORM-моделі, а доменні об'єкти, що забезпечує ізоляцію
  шарів + Observer Pattern для доменних подій — при створенні/видаленні рейтингу автоматично інвалідується кеш і оновлюються
  агрегати курсів через event listeners + Wilson Score Interval для ранжування корисності відгуків — той самий алгоритм, що використовує Reddit
  маніпуляцій: один апвоут не перебиває рейтинг з десятками голосів.

Кешування:
  - Redis використовується і для кешування даних, і для зберігання сесій (замість БД — швидше і горизонтально
  масштабується).
  - Кастомний @rcached декоратор з версіонуванням namespace'ів для точкової інвалідації кешу.

CI/CD:
- PR → dev-pipeline  (test + build + audit + openapi-validation)
- merge - main → main-pipeline → auto semver tag → test changed code → build → deploy staging → E2E tests → pre-release
- after staging deployment trigger - prod-pipeline → deploy live → E2E tests → promote pre-release → stable release → live tag

_можливо є якісь курси в Могилянці які прям допомогли у створенні RateUKMA? Чи може хтось допомагав вам у процесі? (викладачі, старші студенти)_
Проект був ініційований в рамках курсу МРПС, його в наш рік з нуля переробив Сергій Медвідь - тому саме наповнення курсу було дуже актуальним і практичним. (наступне можливо виріжемо хдд) Нам було трооооошки легше, бо ми вже орієнтувались в темі, і нам не треба було розбирати всі концепти з нуля, але ми багато чому корисному навчились.


_для того щоб розкрити трохи як закулісся вашої роботи (якщо вважаєте, що варто суто фокус на проєкт, можемо скіпнути, але як на мене було б цікаво, + цю частину я б вставила прямою мовою):_
_1. Як ви організовували роботу в команді?_
Курс зосереджений на Agile, тому і налаштовували роботу ми в рамках цієї методології - у нас були регулярні щотижневі міти. Ми вели документацію (за неї відповідала Мілана), але згодом ми по-максимуму її автоматизували (наприклад, semantic commits + створення release notes та scheduled DORA метрики у CI/CD). 

В репозиторії у нас є branch protection, і ми робимо командні рів'ю усіх PR-ів. З цим нам допомагали також CodeRabbit AI та Greptilе - дуже корисно для відловлювання багів та едж кейсів. З інших AI-тулів використовували Copilot та Claude Code - не тільки для коду, а і для авто створення баг репортів, тасок і тд.

_2. Чи були якісь кризи або факапи, і як ви їх вирішували?_
Як у багатьох студентів, ніч перед фінальною здачею проекта була довга))  у нас рандомно почали падати е2е тести і ми не могли декілька годин зібрати білд на лайв. Але, на щастя, колективно вночі ми це вирішити)) підключались усі хд

Багато часу також пішло на те, щоб завершити парсер даних по курсах та студентах. Одна з killer features проекту - студент логіниться за корпоративною поштою та одразу бачить усі курси, на яких він був та буде. Цю інформацію треба було звідкись взяти у відкритому доступі, (прим. Каті і Насті - це ми перефразуємо потім), і ми вважали неефективним намагатись брати ці дані з БД адміністрації. Тому ми спарсили весь саз)))) 

_3. Скільки часу пішло від ідеї до першої робочої версії?_
Перший MVP ми презентували на Midterm Presentation - 26 жовтня 2025. Далі ми покращували, і перші відгуки з'явились від друзів-фішників в перших числах грудня - тоді ми здавали проект в кінці курсу. Далі вже покращували якість, дороблювали деякі фічі, і найголовніше - покращували продуктивність та юзабіліті, щоб нічого не лагало, витримувало потрібну юзерів, і ми не переплачували на клауд шалені гроші))

_1. Які функції хочете додати найближчим часом?_
Зараз працюємо над коментарями, плануємо додати конструктор індивідуального навчального плану — щоб студенти могли прямо на платформі складати варіанти розкладу на наступні роки з автоматичною перевіркою кредитних лімітів. Та (можливо) форум для питань по курсах (адже зараз залишати відгуки та реакції можуть тільки ті, хто дійсно слухав курс). Потенційно хотіли б додати feed з новими коментами, але точно треба буде розставляти пріоритети після опитування юзерів, що було б актуальніше.

За 4 доби після запуску платформою скористались 750+ студентів — і до кінця тижня очікуємо 1000!

_2. Чи бачите потенціал масштабувати RateUKMA за межі Могилянки?_
Загалом, схожу логіку можна зробити для будь-якого університета - але потрібно буде підлаштовувати доменну модель курсів та шукати джерело даних. Але поки такого робити не плануємо.
