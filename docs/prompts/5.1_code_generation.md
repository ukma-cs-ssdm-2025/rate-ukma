# Task 5.1 — Code Generation: Personal Plan (ІНП) Backend

Scenario: a student builds their personal study plan (ІНП). They see taken and
mandatory courses by year and semester, add courses from the catalog, mark them
as backup, promote backups and remove picks. The plan is stored on the server.

The prompts below were run in order in Claude Code (CLI), on branch
`feat/#816-personal-plan-api`. The working version is on staging:
https://staging.rateukma.com/plan (sign in with a NaUKMA account; behind the
`fe_personal_plan` feature flag, which is on there).

## Prompt 1 — Backend for the existing UI

### Role
You are a backend developer on our team. The ІНП planner UI already exists
(#807); implement the backend it needs.

### Inputs
- The UI on `feat/#807-personal-plan-constructor-ui`: `src/webapp/src/features/personal-plan/`
  (`planTypes.ts`, `planStore.ts`, `planTimeline.ts`, `planOffering.ts`)
- My drafts: `application_schemas/personal_plan.py`, `services/personal_plan_service.py`
- Plan docs from the earlier tasks:
  - `docs/api/inp-planner-api.md`: the ІНП API contract (task 4.3): endpoints,
    error codes and the rule each one enforces
  - `docs/architecture/decisions/0012-inp-plan-storage.md`: the plan is stored
    on the backend as one record per planned course (task 4.2)
- Conventions: `src/backend/AGENTS.md`, `docs/testing/backend-tests.md`
- A comparable feature to mirror: `views/student_viewset.py`, `services/student_service.py`

### Task
1. Replace the UI's localStorage store with a database model for the student's picks.
2. Add `GET /students/me/plan/` returning the plan in the shape the UI builds:
   study years → semesters → main and backup courses, with credits, weekly
   hours and course type.
3. Add `PUT` and `DELETE` on `/students/me/plan/courses/<course_id>/` to add,
   move, promote, demote and remove a course.
4. Port the plan rules from `planTimeline.ts` and `planOffering.ts` to the service.

### Rules
- Follow the layers used in the project: model → repository (DTOs) → service →
  serializer → viewset, wired through `ioc_container`.
- Endpoint tests cover the six scenarios in `backend-tests.md`.
- Regenerate `docs/api/openapi-generated.yaml`. Pyright and ruff stay clean.
- Do not commit anything.

## Prompt 2 — Plan rules from the requirements

### Inputs
- `docs/requirements/requirements-digest.md` (BR-01…BR-14, PR-01…PR-05)
- `docs/requirements/story_enhance.md`: the ІНП MVP stories US-5.1, US-5.2,
  US-5.9, US-5.10a, US-5.10b
- `docs/requirements/acceptance_criteria_gherkin.md`: scenarios the
  implementation must pass, such as a multi-semester course landing in both
  semesters
- `docs/architecture/decisions/0012-inp-plan-storage.md`
- `docs/api/inp-planner-api.md`

### Task
1. Taken and mandatory courses are always in the plan and cannot be removed or
   made backup (BR-04, PR-01).
2. A course is never in the plan twice (PR-02).
3. A course that runs over several semesters appears in each of them with that
   semester's credits, and is added and removed as a whole (BR-02, BR-08).
4. Totals and limit warnings stay in the frontend.

## Prompt 3 — Choosing the offering automatically

### Task
Hide offerings from the student: they pick a course, and the backend picks the
offering.
- If an offering is profession-oriented for the student's speciality, pick it;
  if there are several, pick the latest.
- If none is profession-oriented, pick the latest offering.
- Store the picked offering on the planned course, the same way `Rating`
  references the offering, and keep `course_id` in the API.

## Prompt 4 — Caching

### Task
Cache the plan in the style of the project: `@rcached` with a versioned
namespace, like `StudentService.get_ratings`. Invalidate it whenever the plan
changes, and keep keys free of personal data.

## Prompt 5 — Showing saved data in Django admin

### Context
The demo must show that data is really saved, without opening the staging
database.

### Task
Add the plan to the admin in the style of `admin/models.py`:
- a list of saved picks, newest first, so a new pick is easy to find;
- the full plan, built by the same service, on the student's admin page;
- picks read-only in admin (deleting allowed), and deleting clears the cached plan.
