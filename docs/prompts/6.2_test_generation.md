# Task 6.2 — Test Generation: Personal Plan (ІНП)

Prompt used in Claude Code (CLI) to add tests to the ІНП planner from the
acceptance criteria. It produced the tests for the gaps found in the existing
suite: the message that a course is already in the plan, decimal sums, an
empty semester, a backup as the only course, the credit limits, and one e2e.

## Role
You are a test engineer on our team. Write tests from the requirements, not
from the code, and prove they can fail.

## Inputs
- `docs/requirements/acceptance_criteria_gherkin.md`: stories US-5.1, US-5.2,
  US-5.9, US-6.3
- Existing tests: `views/test_personal_plan.py`,
  `services/test_personal_plan_service.py`, and `*.test.*` under
  `src/webapp/src/features/personal-plan`
- Conventions: `docs/testing/backend-tests.md`, `docs/testing/e2e-tests.md`

## Task
1. List every scenario of those stories and mark it covered, partly or not
   covered, by reading the existing tests. Write tests only for the gaps.
2. For each gap write the happy path with the numbers from the scenario
   (3.5 + 2.5 = 6), and the edge cases around it:
   - each boundary one step below, on, and one step above (53.5 and 54,
     25 and 25.5, 239.5 and 240.5);
   - an empty state, and a backup that is the only course of a semester;
   - a course the student cannot change (mandatory), a user who is not a
     student, a feature flag that is off, a plan that is still loading.
3. Put the story id in the test or describe name, for example `US-6.3`.
4. Run the tests. Then break the code on purpose, one condition at a time
   (`>=` to `>`, count backups in the totals), confirm the new test turns red,
   and restore the code.

## Rules
- Assert what a user or client observes: rendered text, status code, response
  body, the stored row. Never a mock that echoes its input.
- Backend: pytest with `django_db` and `integration`, factories and existing
  fixtures, `reverse()` for URLs, `freeze_time`, exact status codes, names like
  `test_<method>_<expected>_when_<condition>`.
- Frontend: Vitest and Testing Library. Mock only what is outside the unit
  (router link, auth, feature flags, the plan hook, a dialog that is not under
  test). Never mock the rule being checked.
- E2E: Playwright with the shared fixtures, the feature flag set before
  `goto`, no seeded data: add a course that is not in the plan, check `/plan`,
  remove it, and clean up in `finally`.
- If the app text differs from the Gherkin text, test the app and say so; do
  not change either silently.
- Do not change application code. Format only the files you changed.
- Report the scenario table, the new tests, which mutation each test caught,
  and anything you could not run.
