# Task 5.2 — Fixing and Refactoring

Prompts used after the first version of the ІНП backend, to fix bugs, align
types with the API and the database, and bring the code in line with the
project's style.

## Prompt 1 — Project style

### Role
You are a reviewer who knows this codebase. Make the new code read like the
code around it.

### Task
1. `personal_plan_service.py` has module-level functions, which the project does
   not use. Move them into `PersonalPlanService` as methods.
2. Move the academic-year and timeline helpers into `SemesterService`.
3. `ATTENDED_STATUSES = (ENROLLED, FORCED)` is business logic duplicated in
   several repositories: keep one shared constant and reuse it.
4. Replace the hand-written path-id parsing and error mapping in the viewset with
   the Pydantic validation pattern the other views use.

### Rules
- Behaviour does not change; all tests stay green.

## Prompt 2 — Aligning with the OpenAPI contract

### Context
Regenerating the spec prints enum-collision warnings, and the generated names
(`StatusC33Enum`, `Kind283Enum`) would break webapp types.

### Task
Remove the collisions by renaming the plan's fields rather than adding
`ENUM_NAME_OVERRIDES`: `kind` → `type_kind`, `status` → `year_status`,
`term` → `semester_term`, in both the response and the `PUT` body. Keep the
spec diff purely additive.

## Prompt 3 — Aligning with the database

### Task
1. Link `PlannedCourse` to the offering only, the same way `Rating` is linked.
2. Remove both plan migrations and run `makemigrations` again, so the PR has a
   single `0040_planned_course`.
3. Check for N+1 queries on every plan endpoint, with the plan growing.

## Prompt 4 — Wrong study years

### Context
My account shows six years of study, but I started in 2023.

### Task
Find where `program_start_academic_year_start` comes from and why it is wrong,
and fix how the plan finds the student's first year.
