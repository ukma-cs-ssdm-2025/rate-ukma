# Task 4.3 — API Contracts

## Role
You are a backend engineer. Document and design the API contracts
for the ІНП planner MVP stories. Be precise and minimal.

## Inputs
- Branch `draft/personal-plan-backend` — part of the ІНП API is already
  implemented there. Read first:
  - `src/backend/rating_app/views/personal_plan_viewset.py`
  - `src/backend/rating_app/serializers/personal_plan.py`
  - `src/backend/rating_app/application_schemas/personal_plan.py`
  - `src/backend/rating_app/exception/personal_plan_exceptions.py`
  - `src/backend/rating_app/models/planned_course.py`
  - `src/backend/rating_app/views/test_personal_plan.py`
- `docs/requirements/requirements-digest.md` — entities, lifecycles, rules, prohibitions
- `docs/requirements/results/story_enhance.md` — MVP stories with IDs
- `docs/requirements/results/acceptance_criteria_gherkin.md` — scenarios and rules
- `docs/architecture/decisions/` — ADRs, especially 0004 API format
- `docs/api/api-design.md` — the Error Handling Contract

## Scope
- ІНП planner stories only. Skip parser, analytics and backlog stories.
- Do not design the database schema.

## Output
Write `docs/api/inp-planner-api.md`. Tables and code blocks only,
no introductions or explanations.

1. **Error format:** do not define a new one. Link to the Error Handling
   Contract in `api-design.md` and add a table of ІНП error codes:
   Error code | HTTP status | When it happens | Rule ID from the digest
   Reuse the exceptions already defined in `personal_plan_exceptions.py`.

2. **Endpoints:** one block per endpoint, all under `/v1/`:
   - `METHOD /v1/path` — story ID — `implemented` or `proposed`
   - Auth: who can call it
   - Request: path / query params and body fields with types and required flag
   - Success: status code and response body example
   - Errors: status codes with error codes from the table above

3. **Coverage:** table: Story ID | Endpoint(s) | Status
   Any ІНП MVP story without an endpoint must be listed with a reason.

## Rules
- Implemented endpoints: document them exactly as the code works now.
  If the code conflicts with a story or acceptance criterion, add one line
  `Mismatch:` under that endpoint instead of changing the contract.
- Proposed endpoints: only for ІНП MVP stories not covered by existing code.
  Follow the style of the existing viewset (naming, `require_student`,
  DRF conventions, response shapes).
- Every business rule and prohibition from the digest that the API enforces
  must map to an error code.
- Do not invent fields that are not in the existing serializers or
  required by a story.
