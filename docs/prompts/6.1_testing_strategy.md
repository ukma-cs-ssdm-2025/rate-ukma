# Task 6.1 — Testing Strategy: Personal Plan (ІНП)

Prompt used in Claude Code (CLI) to write the test strategy of the ІНП planner,
next to the project-wide strategy.

## Role
You are a QA engineer on our team. Write a short test strategy for the ІНП
planner that a developer can follow without asking questions.

## Inputs
- `docs/testing/testing-strategy.md`, `backend-tests.md`, `e2e-tests.md`: the
  project-wide strategy; link to it, do not repeat it
- `docs/requirements/acceptance_criteria_gherkin.md`: stories US-5.x and US-6.x
- Backend: `services/personal_plan_service.py`, `views/personal_plan_viewset.py`
  and their tests
- Frontend: `src/webapp/src/features/personal-plan` (`planRules.ts`,
  components and their tests)
- Stack: Django REST with pytest, pytest-django and factory_boy on in-memory
  SQLite; React with Vitest and Testing Library; Playwright on real data with
  no seeded database, behind a Microsoft login

## Output
Write `docs/testing/testing-strategy-planner.md`. One or two pages, no general
testing theory. Open with two lines: it adds to the project-wide strategy, and
the status below is read from test names and bodies, not from a coverage tool.

### 1. Scope
Three tables:
- Automated: Story | Rule | Level.
- Scenario status: Gherkin scenario | covered, partly, not covered, not
  implemented, planned, or `unverified`. Read the tests to decide; do not
  invent coverage.
- Manual on purpose: Check | Why not automated (layout, real Microsoft
  sign-in, real САЗ data, PostgreSQL-only behaviour, accessibility).

### 2. Tools and levels
One table: Rule type | Tool | Why. API tests with a real database for
permissions and mandatory-course rules, unit tests for credit sums, component
tests for the grid, one e2e for add and remove.

### 3. Organization and data
Short bullets: backend test files and their naming and markers, frontend test
location, how tests stay isolated (factories, a transaction per test,
in-memory cache, frozen time), how the e2e creates and removes its own data,
and that no real student data is used.

### 4. Running and checking
The commands for the backend and frontend tests, a note that one command for
the whole repository is planned, and how a test is trusted: break the code on
purpose and expect it to turn red.

## Rules
- Every claim must match the repo. Write `unverified` when you did not check.
- The planner e2e does not exist yet: mark it as planned, not covered.
- Where a story is not implemented in the product, say so; do not list tests
  for it.
- Tests come from the acceptance criteria, never from the code under test.
